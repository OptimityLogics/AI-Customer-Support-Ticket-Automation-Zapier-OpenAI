# Setup Guide — AI Customer Support Ticket Automation

This is the **hands-on configuration guide** for running the workflow in your own Zapier account. It is intentionally different from the project overview in [README.md](../README.md): use this document to connect integrations, configure each step, map fields, and test the automation.

> **Important:** The exported Zap is marked `off` and its steps are paused. The JSON contains account-specific resource IDs (including Slack channels and a Zapier Tables table). Reconnect your own accounts and select your own resources. Only turn the Zap on after every test passes.

## 1. Prerequisites

Before you begin, make sure you have:

- A Zapier account that can create and edit Zaps.
- Access to the OpenAI integration/action available in your Zapier account.
- A Slack workspace and two support channels (one for urgent alerts and one for high-priority alerts).
- Zapier Tables access, or an approved alternative for storing ticket records.
- An email account connected to Zapier that is allowed to send acknowledgements.
- A form, backend, or application that can send an HTTP POST request to a webhook.

Names and available options can vary by Zapier account. If the JSON export cannot be imported in your workspace, recreate the workflow manually using the steps below.

## 2. Review and import/recreate the workflow

1. Open [`workflow/customer-support-ticket-automation.json`](../workflow/customer-support-ticket-automation.json).
2. Download the JSON from GitHub's **Raw** view and keep it as a reference for prompts, path conditions, message templates, and mappings.
3. In Zapier, use an import/transfer feature only if your account supports this export format.
4. If the export format is not supported, create a new Zap and add the trigger, AI action, four priority paths, Slack actions, table actions, and email actions described below.
5. Keep the Zap turned **off** while configuring and testing it.

A workflow JSON file is a configuration reference, not proof that the connected accounts and resource IDs will work in a different workspace.

## 3. Configure the webhook trigger

The first workflow step is **Webhooks by Zapier → Catch Hook**. It expects these input keys:

- `ticket_id`
- `customer_name`
- `customer_email`
- `subject`
- `message`
- `category`
- `plan`

### Setup steps

1. Add **Webhooks by Zapier** as the trigger app and select **Catch Hook**.
2. Copy the unique webhook URL generated by your Zap.
3. Configure your form or application to send a POST request to this URL.
4. Send a test payload, then return to Zapier and test the trigger.
5. Confirm that all seven fields appear in the trigger output with the correct values.

Example test request (replace `YOUR_ZAPIER_WEBHOOK_URL` with your private URL):

```bash
curl -X POST "YOUR_ZAPIER_WEBHOOK_URL" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{
    "ticket_id": "TICKET-1001",
    "customer_name": "Alex Example",
    "customer_email": "alex@example.com",
    "subject": "Unable to sign in",
    "message": "I cannot access my account after resetting my password.",
    "category": "account",
    "plan": "standard"
  }'
```

Use an email address you control during testing. Do not include passwords, payment-card information, API keys, or other secrets in the payload. Do not publish the generated webhook URL in source code or commit it to GitHub.

## 4. Configure OpenAI — Analyze Request

The exported AI step is named **Analyze Request** and uses an OpenAI completion action. It expects the seven webhook fields and is configured to produce these output fields:

| Output field | Expected value |
|---|---|
| `category` | `billing`, `technical`, `account`, or `general` |
| `priority` | `Urgent`, `High`, `Medium`, or `Low` |
| `assigned_team` | The team responsible for the ticket |
| `reasoning` | Brief explanation for classification and routing |

### Configure the step

1. Add the available OpenAI/AI completion action in Zapier and connect your own account if prompted.
2. Copy or preserve the instructions from the JSON export.
3. Map the trigger's fields into the matching prompt inputs:
   - `ticket_id` → webhook Ticket ID
   - `customer_name` → webhook Customer Name
   - `customer_email` → webhook Customer Email
   - `subject` → webhook Subject
   - `message` → webhook Message
   - `category` → webhook Category
   - `plan` → webhook Plan
4. Configure structured output fields if the action supports them. If the action returns only a text block, add a parsing step or map the output carefully before the Paths.
5. Run a test and confirm the values match the allowed categories, priorities, and teams.

### Classification logic in the exported prompt

**Categories and teams**

| Category | Typical issue | Assigned team |
|---|---|---|
| `billing` | Payment, subscription, billing question | Finance Support |
| `technical` | Bug, error, feature request, performance | Technical Support |
| `account` | Login, password, profile, permissions | Account Support |
| `general` | Feedback, question, other request | Customer Support |

**Priority guidance**

- **Urgent:** payment failure, security issue, account blocked, or service unavailable.
- **High:** an important issue from a premium customer or a repeated issue.
- **Medium:** a normal support issue.
- **Low:** a general question or feedback.

Treat AI classification as a recommendation. Review security-sensitive or consequential account decisions instead of relying on the model alone.

## 5. Configure the four priority paths

The workflow contains four conditional paths. Each path checks the AI step's `priority` output using a case-insensitive exact match.

| Path | Condition | Expected behavior |
|---|---|---|
| Urgent | Priority equals `Urgent` | Slack urgent alert, ticket record with `Urgent - Open`, urgent acknowledgement |
| High | Priority equals `High` | Slack high-priority alert, ticket record with `High - Open`, high-priority acknowledgement |
| Medium | Priority equals `Medium` | Ticket record with `Open`, standard acknowledgement |
| Low | Priority equals `Low` | Ticket record with `Open`, standard acknowledgement |

For each path:

1. Select the `priority` field from **Analyze Request** in the condition.
2. Set the comparison to an exact match for the path's priority value.
3. Test with a sample that should match that path.
4. Verify that the correct actions run and that other priority paths do not run.

Add a fallback/manual-review route for missing or unexpected AI output if your Zap editor supports it. This is not a substitute for testing the four configured paths.

## 6. Connect and configure Slack alerts

The exported workflow posts Slack messages for **Urgent** and **High** tickets only.

1. Add or open the Slack message action under the Urgent path.
2. Connect your own Slack workspace.
3. Select the intended urgent-support channel. Do not rely on the channel ID embedded in the export.
4. Verify the message includes ticket ID, customer name, customer email, subject, category, priority, and assigned team.
5. Repeat under the High path, selecting your high-priority channel.
6. Test both actions and confirm the messages arrive in the correct channels.

Limit channel membership to people who need this information. If your policy does not permit customer email addresses in Slack, remove that field from the message template.

## 7. Create and map the Zapier Tables destination

The export writes ticket details to a Zapier Tables table. The table ID in the JSON is specific to the original environment, so select or create a table in your account.

Create columns corresponding to these fields:

| Field / column | Source or value |
|---|---|
| Ticket ID | Webhook `ticket_id` |
| Customer Name | Webhook `customer_name` |
| Customer Email | Webhook `customer_email` |
| Subject | Webhook `subject` |
| Message | Webhook `message` |
| Category | OpenAI `category` |
| Plan | Webhook `plan` |
| Priority | OpenAI `priority` |
| Assigned Team | OpenAI `assigned_team` |
| Status | Path-specific fixed value |
| Created Timestamp | Current timestamp (`now`) |

Configure the create-record action in each path to use the same field mapping, with these status values:

- Urgent path: `Urgent - Open`
- High path: `High - Open`
- Medium path: `Open`
- Low path: `Open`

Test each action and inspect the created row. Confirm that no field is shifted into the wrong column and that the priority-specific status is correct.

**Duplicate handling:** the exported create-record actions do not by themselves guarantee deduplication. If the webhook sender may retry a ticket, add a lookup/update strategy based on `ticket_id` before creating a new record.

## 8. Configure acknowledgement emails

The workflow contains email actions for Urgent, High, and standard (Medium/Low) tickets.

1. Open each email action and connect your own sending account.
2. Set the recipient to the webhook's `customer_email`.
3. Confirm the correct template is used:
   - Urgent: subject begins `Urgent Support Request Received`.
   - High: the message says the ticket has been marked high priority.
   - Standard: subject begins `Support Request Received` or `We Received Your Support Request`.
4. Confirm the customer name, ticket ID, and subject are mapped from the webhook.
5. Test with an email address you control and verify the delivered message.

Add a condition or safe handling step so an acknowledgement is not attempted when the email is missing or invalid. Avoid promising a resolution time unless your support policy authorizes that promise.

## 9. End-to-end test plan

Keep the Zap off until individual steps pass. Test these cases through the Zap editor:

| Test case | What to verify |
|---|---|
| Urgent ticket | Urgent path matches, urgent Slack alert arrives, record status is `Urgent - Open`, urgent email template is selected |
| High ticket | High path matches, high Slack alert arrives, record status is `High - Open`, high email template is selected |
| Medium ticket | Medium path matches, record status is `Open`, standard email is selected, no urgent/high Slack alert |
| Low ticket | Low path matches, record status is `Open`, standard email is selected, no urgent/high Slack alert |
| Missing customer email | Ticket can be stored; email action is skipped or handled safely |
| Unexpected AI output | Ticket is not silently lost; manual review/fallback behavior is clear |
| Duplicate ticket ID | Behavior matches your deduplication policy |

After testing, review Zapier's task history and each step's input/output. Confirm the correct account connections, path conditions, table, Slack destinations, email recipient, and templates. Only then enable the Zap and submit one controlled live test.

## 10. Troubleshooting

- **Webhook receives no data:** verify the Catch Hook URL, POST method, request body, and content type. Send a fresh test request and inspect the sender's response/log.
- **One or more fields are missing:** make sure the JSON keys match the seven expected names exactly, especially `message` (not only `description`).
- **OpenAI returns unstructured text:** configure structured outputs if available, or add a parsing step and map the four expected fields.
- **Priority path does not match:** inspect the actual `priority` output, field selection, whitespace, and spelling. Use the exact values defined above.
- **Slack action fails:** reconnect Slack, select the correct workspace/channel, and confirm the connected account can post there.
- **Table action fails or saves wrong data:** choose your own table, re-map every field, and check the status value for that path.
- **Email action fails:** reconnect the sending account, verify the recipient field, and check provider permissions and spam/sending limits.
- **Copied workflow references old resources:** replace original channel/table references with resources in your workspace and retest every affected action.
- **Repeated webhook requests create duplicates:** add a lookup/update or idempotency strategy using `ticket_id`.

## 11. Pre-activation checklist

- [ ] The webhook captures all seven required fields.
- [ ] OpenAI is connected and returns all four expected outputs.
- [ ] Category, team, and priority values follow the defined rules.
- [ ] All four priority paths have been tested.
- [ ] Urgent and High Slack alerts go to the correct channels.
- [ ] Each path writes the correct status and field values to your table.
- [ ] Email templates, recipients, and missing-email behavior have been tested.
- [ ] Duplicate-ticket behavior is understood and handled if required.
- [ ] No secrets or private webhook URLs are stored in the repository.
- [ ] Data access, privacy, retention, and escalation requirements have been reviewed.

## Security and privacy

- Never commit API keys, passwords, OAuth tokens, private webhook URLs, or customer secrets.
- Send only the information needed to classify and route a ticket.
- Treat customer-provided ticket text as untrusted input.
- Restrict access to Slack channels, email accounts, and ticket tables.
- Review AI-generated classifications before consequential actions and follow applicable privacy and data-retention policies.
